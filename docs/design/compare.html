@convex-dev/migrations 与 convex-improved-migration 对比

左边是官方组件 @convex-dev/migrations（0.3.x，源码按 main 202fa4a 核对），右边是 convex-improved-migration。按促成这个项目的六个问题逐一对照，问题原文见 docs/research/problem-statement.md。

左栏是一个生产应用里用官方组件的典型写法，名字已改写。终端输出为示意。

总览：解决了哪些问题

问题旧组件新方案结果

1. 新部署重放全部近百项

@convex-dev/migrations 0.3.x

要删掉一项，只能自己确认生产已完成，再手工维护归档文档。组件没有"不运行就记为完成"的 API。

convex-improved-migration

已完成的记录按旧组件里的名字保存。这些名字不在新计划里，status 把它们列在 "Removed from the Plan" 下面，对应的代码可以直接删掉。新部署只跑计划里的步骤，每项在空表上只花一个空批次。

解决。"不运行就记为完成"有三条明确的路：跑完、mark-done（必须写原因）、adopt（带条数校验）。组件从不因为"看起来是新库"就自动跳过。

2. 等不到结束，失败也不报错

@convex-dev/migrations 0.3.x

只能用 lib:getStatus --watch 盯着看；runToCompletion 能等，但一次只处理一个迁移。

convex-improved-migration

CLI 持有一个 apply 调用，同时轮询 status 打印进度。npx convex run 的一次调用超过 300 秒就会被客户端放弃（本地后端实测 302 秒），所以一次 apply 调用最多工作 4 分钟，之后把运行交给后台驱动并报 Still running。CLI 接着用 resume 续接同一个运行，Seed 不会重跑，所以长时间的回填不受单次调用时长的限制。e2e 验证了两种情况：一次 312 秒、跨两次 apply 调用的运行退出码为 0；没有开 convex dev 的匿名本地部署上也能跑完。退出码：0 全部完成，1 失败或被拒绝，2 超过 --timeout 但运行仍在继续，64 用法错误。同一部署上第二个 apply 会接管第一个，第一个在下一个批次边界停下并报告被接管。

解决。setup 脚本改成"apply 成功后再 seedDev"即可；CI 用退出码判断。

3. 就绪旗

@convex-dev/migrations 0.3.x

空的新部署读不到旗就走降级路径，所以也得把翻旗迁移跑一遍。

convex-improved-migration

新部署上，这一步在空表上跑一个空批次就算完成。在那之前读到的是旧路径，因为没有旧数据，结果也是对的。isReady 是响应式的，只在步骤状态变化时触发重算，不会每个批次都让查询重跑。

解决。旗表、翻旗迁移、清旗迁移三样东西都不再需要。

4. 导入快照后派生数据不重建

@convex-dev/migrations 0.3.x
convex-improved-migration

检测原理：每次 apply 都取消旧的哨兵调度函数，再预约一个 4 年后才执行的新哨兵，并记下它的 id 和令牌。导入不会恢复待执行的调度函数，所以记录里的哨兵查不到就说明状态是恢复来的。本地 e2e 验证了两种情况：A 的快照导入 B，以及 A 的快照导回 A。下一次 apply 之前，status 报告 importSuspected，已完成的 Rebuild 显示为 pending，check 退出码为 1，isReady 对 Rebuild 返回 false。在控制台取消全部调度函数也会被当成导入。有两种情况检测不到，需要手动执行 rebuild --all 或 rebuild <id>：快照导回同一个部署、而且快照之后没有跑过 apply；只导入单张表（convex import --table）。计数漂移也检测不到。

解决。重建和一次性迁移分开；导入后自动重建，不再靠在 runAll 里"故意留着"。

5. 种子数据

@convex-dev/migrations 0.3.x

而且它只会跑一次。以后新增参考数据，就得再写一条新迁移。

convex-improved-migration

新增国家只需要改 COUNTRIES，下一次部署就会补上。不用写游标，也不用写 dry run 协议。一次性的授权类操作用 m.once("id", run)。

解决。种子从迁移队列里拿出来；生产和 dev 共用一个函数。

6. 剪枝

@convex-dev/migrations 0.3.x

getStatus 默认只返回最新 100 行；状态有一部分来自调度记录，7 天后会变成 unknown。

convex-improved-migration
解决。剪枝就是从计划里删掉步骤。每个部署的 status 都显示 Done 之后就可以删；删早了，没跑完的部署会拒绝执行，不会悄悄跳过。跨部署汇总“哪些已经全部完成”目前没有内置命令，需要逐个部署看 status --json。

其他改进（六个问题之外）

问题旧组件新方案
外层事务中止（超时、OCC 重试用尽）不留错误信息（upstream #5）只看得到调度记录里的 failed，7 天后消失驱动是 action，能看到每个批次的失败并单独写入；e2e 已验证 1 秒超时会被记录为失败
事务超限固定批大小，失败要手动调撞到平台限额自动减半重试，之后每批最多按 1.2 倍恢复；e2e 中 100 → 50 → 25 后跑完。应用代码抛出的错误不会触发减半
本地后端写入限流（每秒 4 MiB）未处理驱动内等待后重试同一批次（1 秒起，翻倍到 16 秒，最多 8 次）；e2e 中约 144 MB 写入触发 12 次限流后跑完
dry run 只看主表（upstream #16）是从已保存的游标开始，列出下一批对任意表的写入，最多 20 条；要从头开始的步骤会在一个回滚的事务里先执行 clear 再预览第一批
同一文件定义迁移又引用 internal 时出 TS2589（upstream #28）会出现步骤是数据，不引用 internal，结构上不会出现
挪文件或改函数名会重跑会，状态按函数路径记录不会，按声明的 id 记录
迁移跑完后的校验每个迁移自己写 verifierneeds 同时用于跳过已处理文档、完成前校验、测试断言。校验发现遗漏时步骤失败，下一次 apply 重新扫描
测试自己拼 runner 调用t.action(internal.migrations.apply, {}) 加 expectNoneNeed
reset 之后原来的处理条数和完成时间丢失会，reset 覆盖 processed、latestStart、latestEndreset 事件里保留之前的状态、完成时间和条数；运行正在处理的步骤拒绝 reset，要先 cancel
